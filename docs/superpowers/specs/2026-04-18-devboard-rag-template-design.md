# 通用开发板 RAG 模板增强设计

## 背景

当前草案生成已经能较稳定地产生核心芯片和主连接关系，也开始具备基础布局与部分外围补全能力，但离“接近可直接打样”的原理图仍有明显差距。主要差距不在于 LLM 是否知道器件名字，而在于真实开发板通常依赖成组出现的外围子电路，例如电源去耦、上拉下拉、复位/启动、下载调试、接口保护、指示灯和扩展排针。

这些外围组合具有较强的模式性，且在嘉立创开源原理图中已有大量可复用参考。继续单纯强化 LLM prompt，收益有限且不稳定。更合适的方向是把 LLM 从“凭空生成完整电路”改成“基于规则与模板的组装器”。

## 目标

- 面向“通用开发板”场景，提高生成结果的工程完整度。
- 在主控、电源、下载调试和基础扩展接口周围，自动补入高价值外围器件组合。
- 在保持现有草案预览与应用链路稳定的前提下，引入结构化模板检索能力。
- 让 LLM 负责需求理解与模板编排，不再独自承担外围器件发明工作。

## 非目标

- 首版不覆盖所有芯片、所有传感器、所有模拟前端。
- 不追求整张参考原理图的直接复制或一键照搬。
- 不尝试在首版完成 ERC/DRC 级闭环设计。
- 不把低置信度模板直接强行落图，避免引入错误外围。

## 设计结论

采用 `规则骨架 + RAG 子电路模板 + LLM 组装` 的三层架构。

工作方式如下：

1. LLM 先生成核心草案，识别用户要的是哪类开发板与功能模块。
2. 规则层为主控、电源、下载等模块补齐最小系统骨架。
3. RAG 层从嘉立创开源原理图中检索相似主控和开发板子电路，补充高价值外围组合与典型取值。
4. LLM 对候选模板做裁剪、冲突消解和组合说明。
5. 预览与应用阶段仅使用高置信度结果，低置信度项以建议方式提示。

## 方案对比

### 方案 A：纯规则模板

优点：

- 落地最快
- 可控性强
- 回归风险较低

缺点：

- 需要不断手工维护型号规则
- 对不同主控变体和上下文适应性弱
- 很难从开源设计中持续吸收经验

### 方案 B：规则骨架 + RAG 子电路模板 + LLM 组装

优点：

- 稳定性和完整度平衡最好
- 既能保证最小系统存在，也能复用真实参考设计
- 可逐步扩展更多主控与开发板家族

缺点：

- 需要新增模板抽取、索引和重排流程
- 工程复杂度中等

### 方案 C：全 RAG 驱动

优点：

- 理论上最接近真实参考设计

缺点：

- 容易召回整图噪声
- 不同参考设计之间合并冲突高
- 缺少稳定兜底

推荐方案为方案 B。

## 首版范围

首版只服务“通用开发板”增强生成，优先提升以下模块：

- 主控最小系统
- 电源入口与 3V3 供电
- 下载调试
- 基础指示与按键
- 扩展排针与常用基础接口

首版重点主控家族：

- `ESP32-S3`
- `ESP32-C3`
- `RP2040`
- `STM32F103`

首版重点外围模块：

- `USB 5V 输入`
- `3V3 LDO`
- `UART 下载/调试`
- `EN/RESET/BOOT`
- `电源灯/状态灯`
- `基础按键`
- `扩展排针`

## 总体架构

### 1. LLM 编排层

LLM 保留以下职责：

- 理解用户要生成的是哪类开发板
- 识别需要的核心器件和功能块
- 在多个候选模板之间做取舍
- 生成预览说明与待确认事项

LLM 不再负责：

- 纯凭经验决定去耦数量
- 纯凭经验决定 EN/BOOT RC 组合
- 纯凭经验决定 UART、USB、电源入口等标准子电路细节

### 2. 规则骨架层

规则层负责保证高确定性的最小系统存在。即使 RAG 未命中，也必须至少输出一份可工作的基础骨架。

规则层补全内容包括：

- 主控 VCC 去耦
- EN/RESET 默认上拉
- BOOT 默认配置
- UART 下载/调试基础接口
- USB 5V 到 3V3 的基础供电路径
- 指示灯限流电阻
- 按键基础上拉下拉

### 3. RAG 模板层

RAG 不检索整张原理图，而检索“子电路模板”。模板粒度控制在可独立复用的功能单元。

首版模板类型：

- `mcu_power_core`
- `mcu_boot_reset`
- `uart_download_header`
- `usb_power_input`
- `ldo_3v3_stage`
- `power_indicator`
- `status_indicator`
- `button_reset`
- `button_boot`
- `expansion_header`

模板应包含：

- 主器件型号或器件族
- 子电路用途
- 参与器件列表
- 连接网络与引脚映射
- 常见阻容取值
- 来源原理图与置信信息

## 数据抽取与模板库

### 数据来源

优先从嘉立创开源原理图中抽取高质量参考设计，首版只接收满足以下条件的样本：

- 主控型号明确
- 原理图结构完整，非残缺示意图
- 电源、复位、下载接口等基础模块清晰可识别
- 器件网络命名较规范

### 抽取对象

每张参考图不直接作为一个检索单元，而是拆成多个模板片段。每个片段围绕一个“锚点主器件”或“功能单元”抽取。

抽取字段建议：

- `template_id`
- `template_type`
- `anchor_device_family`
- `anchor_device_model`
- `scenario_tags`
- `components`
- `nets`
- `pin_bindings`
- `default_values`
- `source_project_id`
- `source_sheet_ref`
- `quality_score`

### 模板片段示例

以 `ESP32-S3` 最小系统为例，可拆出：

- `ESP32-S3 电源去耦组`
- `ESP32-S3 EN 上拉 + RC`
- `ESP32-S3 BOOT 按键 + 上拉`
- `ESP32-S3 UART 下载排针`
- `ESP32-S3 电源灯`

这种粒度比整图召回更利于合并，也更容易做去重。

## 检索策略

首版采用两阶段检索：

1. `召回`
按主控型号、主控家族、开发板场景标签召回模板。

2. `重排`
结合当前草案上下文做二次排序。

重排信号包括：

- 主控型号精确匹配
- 器件族匹配
- 当前草案是否已有等价子电路
- 当前草案已有网络名是否匹配模板
- 用户需求是否需要下载调试、状态灯、扩展接口

召回优先级：

1. 具体型号模板
2. 同家族模板
3. 通用开发板模板

## 模板合并策略

模板合并必须是结构化的，而不是把参考设计文本直接拼接到 prompt 中。

合并流程：

1. 基于核心草案识别锚点主器件。
2. 为每个锚点主器件匹配规则骨架。
3. 为骨架查询 RAG 候选模板。
4. 对候选模板做去重、冲突检查和数值优先级裁决。
5. 只将高置信度模板转换为草案组件、引脚、网络。
6. 将低置信度模板记录为“建议补全项”，显示在预览说明中。

冲突处理原则：

- 已有等价器件时不重复生成
- 已有网络名时优先挂接现有网络
- 模板数值冲突时，优先采用更接近主控官方参考设计的值
- 多模板冲突无法判定时，降级为建议项，不直接落图

## 置信度策略

首版必须显式区分高置信度和低置信度。

高置信度的条件：

- 主控型号精确命中
- 模板类型属于开发板基础模块
- 当前草案缺失该功能块
- 模板与现有网络/引脚映射一致

低置信度的条件：

- 仅命中同家族或近似型号
- 模板含有多种可选数值且无法判定
- 当前草案已有近似模块但结构不完整

输出策略：

- 高置信度：直接并入草案
- 低置信度：展示为建议，不自动应用

## 与现有链路的集成点

建议在当前 `generateDraftPlan` 之后、`previewDraftPlan` 之前插入新的模板增强阶段。

推荐流程：

1. `LLM 生成核心草案`
2. `规则外围补全`
3. `RAG 模板检索与合并`
4. `预览摘要生成`
5. `器件搜索与应用`

这样可以保持：

- 预览与应用基于同一份增强后草案
- 现有布局、网络标签、手动器件确认流程可继续复用

## 数据模型扩展

建议给自动补全对象增加更细的来源标记。

组件字段建议扩展：

- `properties.generated_by = "llm" | "rule_completion" | "rag_template"`
- `properties.template_id`
- `properties.template_type`
- `properties.template_confidence`
- `properties.template_source_project`
- `properties.completion_role`

预览摘要建议扩展：

- 新增模板补全器件数量
- 规则补全与 RAG 补全的分类统计
- 高置信度自动落图项
- 低置信度待确认建议项

## UI 与预览

预览阶段建议增加“参考设计补全”摘要，例如：

- 已补全 `ESP32-S3` 最小系统去耦与启动电路
- 已补全 `USB 5V -> 3V3` 供电与状态灯
- 已补全 `UART` 下载调试接口
- 发现 2 个可选模板，因置信度不足未自动落图

这样用户能理解这些外围并非 LLM 凭空生成，而是来自规则和参考模板。

## 测试策略

首版测试覆盖应包括：

- 型号精确命中时的模板落图
- 家族回退时的低置信度建议输出
- 已存在去耦/上拉时的去重
- 多模板冲突时不直接落图
- 预览摘要能正确区分 `rule_completion` 与 `rag_template`
- 增强后草案仍可复用现有应用、布局和网络标签流程

## 风险

- 开源原理图质量参差不齐，模板抽取容易带入噪声。
- 同一型号开发板存在多种实现，模板数值并不总是唯一。
- 如果模板粒度过大，会导致合并复杂度高和误补器件增多。
- 如果模板粒度过小，召回虽准，但覆盖效果不明显。

## 决策

- 检索粒度选择“子电路模板”，不选择整图 RAG。
- 先聚焦“通用开发板”而不是全品类产品。
- 首版优先支持高频主控家族和基础开发板模块。
- 低置信度模板不自动落图，只提示用户。

## 分阶段落地建议

### 第一阶段

- 在现有规则补全基础上扩展开发板最小系统骨架
- 完成模板数据结构与本地检索接口定义
- 用少量人工整理模板先打通链路

### 第二阶段

- 从嘉立创开源原理图批量抽取模板
- 增加召回、重排和冲突裁决
- 在预览中展示模板来源与建议项

### 第三阶段

- 扩展更多主控家族
- 引入更丰富的接口与外设模板
- 评估是否需要服务端检索与质量评分闭环

## 结论

对“通用开发板”场景，单纯依赖 LLM 生成外围器件组合的上限较低，且稳定性不足。采用 `规则骨架 + RAG 子电路模板 + LLM 组装` 的方案，可以把最小系统稳定性、真实参考设计复用能力和后续扩展性放在一个合理平衡点上。首版先围绕高频主控开发板打深，再逐步扩展到更多芯片与场景。
