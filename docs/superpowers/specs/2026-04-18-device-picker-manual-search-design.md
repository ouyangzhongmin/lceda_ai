# 器件确认弹窗手动搜索兜底设计

## 背景

当前器件确认弹窗中的“搜索候选”直接使用草案里的默认搜索词。该搜索词由 LLM 生成，存在生成错误或不够精确的情况。用户在现有界面中无法覆盖本次搜索文本，只能反复点击默认搜索，导致候选列表为空或偏离预期时没有可行兜底路径。

本次改动目标是在不改写草案默认搜索词的前提下，为单个待确认器件提供一次性手动输入搜索词的入口，用于本次候选搜索。

## 目标

- 保留当前默认搜索词展示与现有候选选择流程。
- 为每个待确认器件提供可折叠的手动搜索输入入口。
- 手动输入的搜索词只影响本次搜索，不回写到草案的默认搜索词。
- 默认搜索失败或搜索词错误时，用户可以快速修正并重新搜索。
- 搜索完成后保留用户输入，便于继续微调关键词。

## 非目标

- 不修改 LLM 生成默认搜索词的逻辑。
- 不将手动输入的搜索词持久化到 DraftPlan 的 `preferred_search_query`。
- 不改变候选卡片、候选选择、自动应用首选候选等既有流程。
- 不新增跨器件共享的全局搜索词编辑能力。

## 方案对比

### 方案 A：纯前端本地临时状态

iframe 自行维护每个器件卡片的展开态与输入值，点击搜索时把手动输入作为参数传给 runtime。

优点：
- 初始实现最快。

缺点：
- 面板状态重新同步、重渲染或关闭再打开时，输入内容容易丢失。
- 与当前 `devicePicker` 的状态驱动模型不一致，后续扩展会变复杂。

### 方案 B：将手动输入状态纳入 `MainPanelState.devicePicker.items`

在每个器件项中增加手动输入相关字段，由 runtime 管理、iframe 渲染。

优点：
- 状态稳定，和现有面板同步机制一致。
- 后续扩展“清空输入”“保留最后一次尝试词”“空结果引导”等能力时无需返工。

缺点：
- 需要扩展状态模型与 runtime 入口，改动面稍大。

### 方案 C：展开态前端本地、搜索词仅点击时传参

把展开态和输入值保存在 iframe，runtime 只接受搜索时的覆盖参数。

优点：
- 比方案 B 简单。

缺点：
- 状态来源分裂，后续维护成本高。
- 输入保留和重渲染行为不稳定。

### 结论

采用方案 B。该方案与当前状态驱动 UI 一致，能稳定承载“手动词只覆盖本次搜索”的需求。

## 交互设计

### 卡片结构

每个待确认器件卡片保持现有信息：

- 器件位号与角色
- 当前状态
- 默认搜索目标
- 已选器件或候选列表

在“搜索候选”按钮旁新增 `手动输入` 按钮。

### 手动输入区行为

- 默认收起。
- 点击 `手动输入` 后，仅展开当前器件的输入区。
- 输入区包含：
  - 一个文本输入框
  - `用此关键词搜索` 按钮
  - `取消` 按钮
- 输入框默认值为空，不自动填入默认搜索目标。
- placeholder 使用明确引导，例如：`输入你想搜索的器件关键字`

### 搜索规则

- 点击 `搜索候选` 时，继续使用默认搜索目标。
- 点击 `用此关键词搜索` 时：
  - 若手动输入去除空白后非空，则优先使用手动输入搜索。
  - 若手动输入为空，则回退到默认搜索目标。
- 手动搜索属于单次覆盖，不修改界面中的默认“搜索目标”展示文本。

### 搜索后状态

- 搜索成功后，候选列表按实际使用的搜索词刷新。
- 输入区保持展开。
- 输入框保留用户刚刚输入的文本，便于继续调整关键词。
- 点击 `取消` 时，仅收起当前输入区，不清除已加载候选列表。

## 状态设计

扩展 `MainPanelState.devicePicker.items[*]`：

- `manualQueryExpanded?: boolean`
- `manualQueryDraft?: string`

说明：

- `manualQueryExpanded` 仅控制当前器件卡片的输入区是否展开。
- `manualQueryDraft` 保存用户当前正在编辑或最近一次用于搜索的手动词。
- 两个字段属于面板 UI 状态，不同步回 DraftPlan。

## Runtime 设计

### 新增或调整能力

runtime 需要支持以下能力：

- 更新单个器件项的手动输入展开状态。
- 更新单个器件项的手动输入文本。
- 在执行器件候选搜索时接收可选的 `manualQuery`。

### 搜索执行逻辑

当前逻辑是直接使用组件的 `preferred_search_query`。改动后顺序调整为：

1. 优先取调用参数中的 `manualQuery.trim()`
2. 若不存在有效手动词，则回退到 `preferred_search_query`
3. 两者都为空时，提示用户当前器件缺少可用搜索条件，请手动输入关键词

### 结果展示逻辑

候选展示中的 query 应使用“本次实际搜索词”，而不是固定展示默认搜索词。这样候选解释和搜索操作保持一致。

### 数据边界

- `DraftPlan.components[*].properties.preferred_search_query` 不允许在本次功能中被修改。
- 手动词只存在于 `MainPanelState.devicePicker.items[*]`。

## Iframe 设计

### 渲染

在器件确认弹窗渲染每个 item 时：

- 根据 `manualQueryExpanded` 决定是否渲染输入区
- 输入框值绑定 `manualQueryDraft`
- `手动输入`、`用此关键词搜索`、`取消` 分别调用对应 runtime 方法

### 按钮禁用

保持现有 `devicePickerBusy` 行为：

- 搜索期间禁用弹窗内除关闭按钮外的操作按钮
- 如输入框支持 `disabled`，应与忙碌态一致，避免重复提交

## 错误处理

- 默认搜索词为空且手动词也为空时：
  - toast 提示：`当前器件缺少可用搜索条件，请手动输入搜索关键词。`
- 搜索结果为空时：
  - 保留输入区与输入内容
  - 不自动收起
  - 保持“尚未加载候选列表”一类区域可继续承载空结果态或后续重试结果

## 测试设计

### Runtime 单测

至少覆盖以下场景：

- 提供 `manualQuery` 时，搜索优先使用手动词
- 未提供 `manualQuery` 时，继续使用默认搜索词
- 手动词为空字符串时，回退到默认搜索词
- 手动词搜索不会改写 DraftPlan 中的 `preferred_search_query`
- 默认词和手动词都为空时，返回可读提示

### UI / 状态测试

至少覆盖以下场景：

- 点击 `手动输入` 可展开当前器件输入区
- 编辑输入框可更新 `manualQueryDraft`
- 点击 `取消` 仅收起输入区，不影响候选数据
- 手动搜索后输入值仍保留

## 风险与约束

- 现有 `devicePicker` 的渲染和事件都集中在 `plugin/iframe/index.html`，需要谨慎控制 DOM 改动范围，避免影响候选选择和批量搜索按钮。
- `devicePicker` 状态会被持久化，因此新增字段必须保持可选且向后兼容，避免旧状态恢复失败。
- 候选解释文案若切换为本次实际搜索词，需要确认不会误导用户把“手动词”理解为新的默认搜索目标。

## 验收标准

- 用户可以在任一待确认器件卡片中展开手动输入区。
- 用户输入任意关键词后，可基于该关键词触发一次候选搜索。
- 搜索结果仅影响本次候选列表，不会改写默认“搜索目标”展示。
- 用户关闭并重新展开当前卡片时，输入值仍可见，直到本次面板状态被用户重置或会话结束。
- 默认搜索流程、候选选择流程、草案应用流程不回归。
